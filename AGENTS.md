# Project Instructions

`CLAUDE.md` imports this file (`@AGENTS.md`) and `GEMINI.md` is a symlink to it, so every agent reads the same conventions. Edit `AGENTS.md`.

**At the start of every session, print the full absolute path of the `AGENTS.md` you loaded and its `last_modified` date** (front matter), so a stale or wrong copy is caught before it steers the work. Bump `last_modified` whenever you edit this file.

Keep this file as short as it can be and still work, and **under 24,000 bytes** (`wc -c AGENTS.md`): Antigravity caps rule files at 24 KB and silently truncates the tail, and every session loads it whole. Add a rule the first time something bites, say it once in the fewest words that carry the *why*, rewrite or trim an existing rule rather than appending beside it, and delete one that has stopped biting. Incident narratives belong in commits.

## Style

- Preserve existing code style unless there are correctness issues. Keep comments brief: the non-obvious *why*, not the *what*, matching the existing comment style.
- Use `if test` rather than `if [`. In `shrc` and `shrc.*`, use the existing helpers (`error`, `warn`, `have_command`, `is_function`, `gets`, `puts`).
- Long flags take both `--option argument` and `--option=argument`.
- **Shell support tiers.** A change lands by tier; tier is capability/commitment, not the order features arrive, and it's per-shell, not per-file — `shrc` spans several tiers by degradation (`$shell` guards plus the failsafe short-circuit).
  - **Tier 1 — zsh** (`shrc`), with **mesh** (`config/mesh/env.mesh` + `rc.mesh`) as the committed target. New functionality isn't done without zsh. mesh is built *toward*, not a merge gate while pre-1.0: a scoped `TODO:` or a `TODO.md` deferral is fine where mesh lacks a feature (the #314 zsh-only ghost text is the pattern); it graduates to gating as it matures.
  - **Tier 2 — fish** (`config/fish/config.fish`), **nushell** (`config/nushell/config.nu`), **Elvish** (`config/elvish/rc.elv` + `lib/interactive.elv`): kept at parity as a *fast-follow*, not a merge gate. A Tier 1 change may land first; port when practical, and don't hold Tier 1 back for them.
  - **Tier 3 — bash** (`shrc`): the ephemeral-SSH fallback, so always a correct, usable shell with a guaranteed floor (`shrc_bash_test.sh`), but capability-capped — what it can do, not zsh-only frills like ghost text.
  - **Tier 4 — dash/`sh` and ksh** (mksh, OpenBSD ksh, ksh93): failsafe only, never a feature target. `shrc`'s failsafe short-circuit routes them to a bare prompt; they must source cleanly and reach the failsafe (`dash -n shrc`, `mksh -n shrc`, `shrc_ksh_test.sh`). mksh is the ksh proxy — most-shipped, most POSIX-strict; ksh as `/bin/sh` was already covered by the `is_sh` failsafe.
  - **`vcs` owns VCS *status* wherever the rich prompt runs** (tiers 1–3; the failsafe returns before any VCS logic loads): the branch/dirty/ahead-behind segment and backend queries — present → shown, absent → a plain prompt, never reimplemented per shell. One scoped exception, for project-root *detection* only: `config/nushell/config.nu` walks parents for `.git`/`.hg`/`.jj`/`.citc`/`.p4config` when `vcs` is absent so `inside-project`/session startup still work; `shrc.vcs` doesn't (it returns no root). That's marker detection, not status logic, and a per-shell choice, not a cross-shell invariant to replicate.
- **mesh config**: kebab-case names (`have-command`, `tilde-pwd`) to match mesh's vocabulary; anything a non-interactive `mesh script.mesh` needs goes in `env.mesh`, not `rc.mesh`; everything above `rc.mesh`'s interactive section stays side-effect free so `mesh -c 'source .../rc.mesh'` stays testable.
- **Elvish config**: kebab-case too. Elvish resolves names at compile time, so define a function above every use. Everything naming `$edit:` belongs in `lib/interactive.elv` — `$edit:` exists only with a terminal, so naming it in `rc.elv` fails the whole file under `echo cmd | elvish`. Keep `rc.elv` definitions-only above its interactive block so the harness loads it without a pty. Where Elvish has no equivalent (job control, a directory stack, `source`, a non-interactive environment file), leave a `TODO:` in place rather than dropping the feature silently.
- **Session-manager startup** lives behind `want_tmux`/`want_shpool`, `session_backend`, and the `autosession`/`autotmux`/`autoshpool` wrappers: shpool by default, tmux when shpool is missing or `WANT_SHPOOL=0`; `SESSION_BACKEND=tmux` flips the preference (tmux preferred, shpool fallback). Keep it in parity across `shrc`, fish, nushell, mesh and Elvish, per the tiers.

## Testing

- Add or update tests with any code change — in the module's existing test file, else a new one following the project's conventions. A task isn't complete without them.
- Run `make test` after any change touching executable behavior, and before committing. A docs-only change (Markdown, comments, this file) doesn't need it — say that's why you skipped it.
- Changing VCS or prompt functions: run the performance tests, include timing, and warn of any regression.
- Per-VCS subcommand behavior (git/hg/jj) lives in the `vcs` Go binary in the `vcs/` submodule (https://github.com/mikelward/vcs); test subcommand semantics there. `make test` builds the submodule binaries.
- Touching `config/nushell/*`: install `nu` locally so `config/nushell/config_test.nu` runs rather than skipping.
- Prefer direct binary downloads (GitHub releases) or `cargo install` over `apt`, pinned with a checksum, so red CI means "the config broke", not "upstream moved". `apt` is fine where upstream publishes no binary to pin (`install-ci-shells.sh` takes it for zsh alone).
- **Fix preexisting test failures as the *first* commit of the series**; don't stack on a red baseline. If one is genuinely unrelated and out of scope, say so up front and confirm before skipping it.
- **No `sleep`, retry loops or bumped timeouts** for flaky/racy tests — make the ordering explicit or fix the race; "passes most of the time" is broken. **Never disable a failing check** — fix the underlying issue.

## Talking to the user

- **One question at a time** — the most important first; wait for the answer, then ask the next if still needed. Ask in plain chat or through your client's question tool (`AskUserQuestion` in Claude Code, `ask_question` in Antigravity). Never ask while the user is still typing.
- **After asking, stop and wait**: don't proceed on an assumed answer, pick a "recommended" option yourself, or keep working on the part the question affects.
- **Answer a mid-turn message first** — the "sent while you were working" interjection gets your very next output, before any further tool call, even if it's one sentence. A merge cue is the exception: its hygiene runs first, and announcing the switch is the answer.
- **Message only when the user needs to see it** (maintainer, 2026-10-15): each notifies their phone. Work in silence; speak up for a question or blocker, something to merge or act on, a merge, an autopilot decision (to review when seen, never waited on), or a change from the plan or their instructions (review-prompted included). Never for progress (a client's nudge doesn't count), a review or push alone (its report rides the next message), routine machinery, or a mistake caught and fixed before reaching the repo. The session-start `AGENTS.md` line still opens every session.
- **Keep replies short**: lead with the most important point; if there's more, ask whether they're ready for the next one.
- **End the turn by restating any pending decision** — a question you asked, or a guess autopilot recorded for review — as the last line, written out in about a sentence (a back-reference isn't actionable), every turn until it's answered. Nothing pending, no line.

## Git

- Use `git worktree` when available, one per branch, so work on one branch isn't disturbed by another.
- **One commit per logical change.** Rewrite unmerged commits freely — amend, `git commit --fixup` + autosquash, squash, reorder, split — folding fix-ups and review responses into the commit they belong to; no `wip` / `fix typo` / `address review` churn reaches `main`.
- **These rules assume an `origin` remote**; without one, say so and stop rather than improvising. **Exception:** a sandbox with intentionally no remote Git (Codex cloud) follows the branch rules from the current `HEAD` (a pre-created working branch counts), commits locally, and reports fetch, push and PRs unavailable, using its own PR handoff if any. That outranks every `origin`-dependent step (merge-cue fetch, branching off `origin/main`) — name what wasn't possible, don't fake it. But a merge cue needs a base *containing* the merge: say the follow-up needs a fresh sandbox or synced checkout rather than branching off a `HEAD` whose commits just landed.
- **Branches**: `<agent>/<short-topic>` (`claude/...` Claude Code, `gemini/...` Gemini / Antigravity, `codex/...` Codex) off `origin/main`, one topic each, never committing to `main`; don't hard-code `claude/` unless you *are* Claude Code.
- **Your `<agent>/` branches are yours**: create freely; push, `--force-with-lease`, rename and delete those this session created or was assigned — no permission, announcement or per-branch confirmation (this file is the standing grant, so don't re-ask). Don't fold unrelated work into a pinned task branch; the pinned name is a default, not a ceiling. Any other branch, or `main`, is a conversation.
- **Merge cue (`merged` / `I merged` / `landed` / merge webhook) runs hygiene *before* the rest of the message**: fetch main if the sandbox can (`git fetch origin +refs/heads/main:refs/remotes/origin/main`; a bare fetch leaves a single-branch clone's `origin/main` stale), cut a fresh `<agent>/<short-topic>` off `origin/main`, announce the switch.
- **Committer line**: the agent authors; a squash or rebase merge rewrites the committer to whoever merged — expected. Never re-author or amend merged commits to "fix" it, and don't narrate it (no note, no offer). It is not a finding.
- **No model identifier**: never name the coding agent's model or version (`Opus 4.8`, `Sonnet`, `Gemini …`, `claude-*`, `gemini-*`) in a commit, PR, comment, or pushed artifact; keep it to chat. Generic attribution (`Co-Authored-By: Claude` / `Gemini`, `Claude-Session:`, "Generated with Claude Code") is fine.
- **Unshallow before answering anything that depends on history depth** — a shallow clone makes `git rev-list --count`, `git log` past the boundary and blame silently wrong. The session-start hook runs `scripts/unshallow.sh` only in Claude Code; elsewhere run it (or `git fetch --unshallow`) yourself first. `--unshallow` exits 0 even when it deepened nothing, so if `git rev-parse --is-shallow-repository` still says `true`, say the history is truncated instead of quoting a count.

## Error handling

- **Don't silently swallow errors**: no bare `2>/dev/null`, unchecked exit status, or `|| true`. Report through `error` / `warn` with enough context to say what failed and why, clean up what the failed step created (temp files, half-written config, a partial symlink), and decide explicitly what the caller sees (a non-zero exit, a fallback value, a skipped step). To ignore a specific failure, name the reason in a one-line comment (`# not every host has shpool`) rather than a bare redirect. Keep behavior identical across `shrc`, fish and nushell.

## Privacy

- **Never put user data in an artifact that leaves this machine** (commit subjects and bodies, PR titles / descriptions / comments, review replies, branch names, code comments, test fixtures): hostnames and internal domains, paths containing the user's real name, work machine names, SSH host aliases and keys, tokens or API keys in shell config, private remote URLs, shell history excerpts. Use placeholders (`/home/user`, `host1`, `git@example.com:org/repo.git`); paraphrase a bug report rather than quote it; when in doubt, ask before pushing.
- **Shell output is not one of those artifacts**: prompts, warnings and help text print on the user's own terminal, where naming hosts, paths and remotes is usually the point. Redact only secrets (tokens, keys, passwords in URLs). Two limits: quoting that output into a commit, PR or fixture republishes it, so the bullet above governs again; and where the full value adds nothing, shortening it stays a judgment call (the fzf loader names the basename, not the `$HOME` path — still right).

## Autonomy

- **Open the PR without being asked** — push and PR are one step — unless told not to ("just commit", "no PR yet"), which holds until lifted. This file is the owner's standing request, so a client rule "open a PR only when asked" is already satisfied, per branch.
- **Watch your own PRs by subscription plus one scheduled check.** Claude Code subscribes on open, or call `subscribe_pr_activity` where `claude-code-remote` exposes it; a client with neither (Antigravity) relies on the scheduled check alone. It misses CI *success*, pushes, the merge, Codex's clean verdict (a reaction) and Codex never answering, so keep exactly one check armed while the PR is open (each costs a model turn): `send_later` in Claude Code, `schedule` with `DurationSeconds` in Antigravity (cancel via `manage_task` `kill`). Under drive, arm auto-merge at open only where the ruleset requires the Codex verdict AND resolved conversations — with CI alone it merges before Codex answers, and an open comment holds nothing back.
  - Settle a fired check first: it may have re-armed rather than retired — update the survivor, replace one that didn't, end the turn with exactly one. Check the fire time you got against the one you asked for (4 minutes has come back as 64); prefer a relative delay, since an absolute time from this container's clock can be rejected as past; re-time it or say the watch isn't armed. Minutes while CI or Codex is out or after a push, longer once only a human is left. Name the PR and what to re-read, not a SHA or a list of open PRs, which go stale.
  - **`dirty` — always — or `behind` where branches must be up to date** needs a rebase and a lease-guarded force-push. Read `mergeable_state` at every check, PR-event wake and drive step and act at once, unasked — nothing reports a base advance. Fetch both refs by refspec, unshallow, rebase onto the fetched `origin/<base>` (not always `main`, never the local branch). Confirm before rebasing that your branch has every remote head commit, and before pushing that the head hasn't moved since the tip you noted before fetching — the push flags don't reliably refuse a rewind, an unfetched commit, or one fetched and not rebased onto. If either fails or you can't tell, stop and ask.
  - **Wake PRs a merge leaves behind.** At your first turn after your PR merges (by hand or auto-merge), message every other open PR on that base that another session drives (its body ends with the session URL), naming that PR and saying only that its base now points at `<sha>`, the post-merge tip — whatever its state reads, since GitHub may still be computing mergeability. Name no merge and no other PR: an older copy of these rules reads either as its own merge cue. Receiving one, fetch base and PR head by refspec (unshallow) and test that head against the fetched tip, not `<sha>`, which a later merge may have passed: `behind` if `git merge-base --is-ancestor <tip> <head>` exits 1, `dirty` if `git merge-tree --write-tree` (Git 2.38+) exits 1; any other exit is a failure to report. Your rules decide the rebase. Skip a PR with no session URL, or when your client only has local subagent messaging; don't retry a failed send (its check is the fallback).
  - Merged or closed: one last reply-and-resolve pass (reviews land after merges). On a merged PR anything real goes to a follow-up PR named on the thread before you resolve; closed-unmerged, answer, resolve, open nothing. Then cancel the check and unsubscribe, if subscribed — `list_triggers` spans the account, so match session and PR first (an update reschedules what it matches as surely as a delete cancels it).
- A scheduler or GitHub prompt: say so once and carry on (a settings file written mid-session can't fix this session).
- **"Drive"**: pick the next task, implement it, open the PR, send it for review, address every comment, merge once CI is green and Codex's verdict for the current head is in, repeat — until the work runs out or the user says stop, not when one PR merges.
- **A red baseline is the next task**: before pulling from `TODO.md`, get the suite green. A preexisting failure is work, not "unrelated" to step around — that call goes wrong and leaves every later PR on an unverified tree.
- **"Autopilot"** is drive without blocking: wherever drive would ask, take the cheapest-to-undo guess, recording each in `TODO.md` under `Decisions needing review` (what, the alternative, why reversible; create the file or heading if missing). It outranks stop-and-wait. Destructive or irreversible acts *outside* the loop (rewriting shared history, deleting work, anything beyond this repo) still wait for a real answer; the loop's own steps (commit, push, PR, merge a green PR) never stall it. Privacy uncertainty (a home path, hostname, private remote, token) is never inside the loop — a push can't be un-published, and a `TODO.md` note doesn't retract it.

## Pull requests

- Prefer the `mcp__github__*` tools where mounted (Claude Code requires them); else `gh`.
- **Update the PR title and body before each push** (body first) to the full branch diff against `origin/main`, and post the PR link in the next message after the push. With no PR yet, push, then do this as soon as one is opened.
- Several open PRs on a feature: list every one by URL, one per line (the "View PR" chip shows only the first, anthropics/claude-code#46625).
- **"Drive to merge"**: open the PR, wait for Codex, address every comment (fix it, or reply on the thread why not), merge on green CI plus Codex's verdict for the current head.
- **Ordered work ("next", "then", "after that", "follow-up")** may open in parallel but merges only after every earlier item this session was given and any PR the paragraph names has merged — any repo, no time cap; if one won't finish, hold it and ask, autopilot included; no auto-merge on it until then (auto-merge can't see the order). Read the list from the session's record, not memory.
- **Codex is the automated reviewer** (not Copilot), triggered automatically; request it only to confirm a rebutted false positive or as the verdict rule allows. Address its comments unasked, folding each fix into its commit; defer a real out-of-scope finding (below).
- **Judge every comment on merit**: verify before acting; if it doesn't hold, reply why and decline. A cited rule is a *reading* — check what it says. Codex misreads the privacy rules toward strictness, quietly costing capability: quote and decline rather than narrowing the code. A real rule-vs-need conflict is the maintainer's call, not yours either way. Declining doesn't clear `codex`: post the rebuttal, then poke as the verdict rule allows (or let the next push, if the rebuttal is up first); escalate if it re-raises.
- **A second verified finding in the same mechanism is a design question**: look for the shape elsewhere and ask whether a design change deletes the class; say what you chose on the thread (the maintainer's call, autopilot included).
- **Never silently dismiss a thread**: answer (a disagreement is an answer — say why), then resolve once the fix is on the head or it's rebutted; anything still to do stays open. Acknowledgment beats silence. Push, reply citing the sha, resolve — `resolve_review_thread` or `gh api graphql` `resolveReviewThread`, with `PRRT_*` from `review_threads[].id`, not `PRRC_*`.
- **Restate every finding in your next message**: one bullet each (review comment, top-level comment, review body), most blocking first — claim, where, action or the options. This outranks *keep replies short*; ask only the most blocking question.
- **Defer a real out-of-scope finding** without asking to merge past it: `TODO.md` entry, commit and push, reply citing the sha, resolve (a threadless finding skips only the resolve). The push re-triggers Codex; poke only as allowed; escalate if it re-raises.
- **Read the Codex verdict, don't infer it**: its PR-body reaction (`issue_read` → `reactions`; a thread's `Useful?` bar reads true on any PR it touched) — `eyes` reading, `+1` clean, revoked on push, so a visible one belongs to the visible head; `+1` on green CI is a merge. Findings arrive as review comments or a top-level comment (`get_review_comments` is inline-only — read `get_comments` too) and gate whatever the reaction says. A pending `codex` status means findings to address; a clean review with no reaction or an unanswered rebuttal (poke `@codex review` five minutes later); or a hung review — nothing back five minutes after the push, or stuck at running (👀) ten minutes on (poke). A poke that hangs the same way gets a second an hour later; escalate only if that one hangs too, never after one (maintainer, 2026-10-22). Leave PR-body reactions to Codex (the count is anonymous).
- **Once Codex +1s a head, make no unnecessary change without asking** (maintainer, 2026-10-13); a necessary one — a rebase for `dirty` or required `behind`, a red-CI fix — and drive or autopilot steps, where in effect, go ahead.
- **Skip your own echoes silently**: a reply you posted via the GitHub MCP returns as an event from the same identity; if the body matches what you just posted, continue.

## CI

- Report significant CI timing regressions after CI finishes on a push (rule of thumb: >25% or >30 s on a job under ~5 min), comparing the same job on the same kind of ref (PR vs PR, `main` vs `main`); name the likely cause (a new dependency, a slow new test, cache invalidation). Don't narrate routine wobble.

## Language, cost and reliability

- **US English** wherever people read English — shell output and help text, commit subjects and bodies, PR titles and descriptions, comments, identifiers: `color`, `behavior`, `canceled`, `gray`. Third-party API spellings stay as those APIs spell them.
- **Call out cost and reliability up front** for a new external dependency (a tool the config calls out to, a network lookup, a third-party service): a rough dollar figure (free tier vs paid, $/month at expected use), new failure modes, rate limits, latency, and what the user sees if it's missing or down. Shell startup is the hot path, so state any latency added to a new prompt. If the impact is effectively zero, say so rather than omitting the note.
