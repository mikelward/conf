# Project Instructions

`CLAUDE.md` imports this file (`@AGENTS.md`) and `GEMINI.md` is a symlink to it, so every agent reads the same conventions. Edit `AGENTS.md`.

**At the start of every session, print the full absolute path of the `AGENTS.md` you loaded and its `last_modified` date** (front matter), so a stale or wrong copy is caught before it steers the work. Bump `last_modified` whenever you edit this file.

Keep this file as short as it can be and still work, and **under 22,000 bytes** (`wc -c AGENTS.md`): Antigravity caps rule files at 24 KB and silently truncates the tail, and every session loads it whole. Add a rule the first time something bites, say it once in the fewest words that carry the *why*, rewrite or trim an existing rule rather than appending beside it, and delete one that has stopped biting. Incident narratives belong in commits.

## Style

- Preserve existing code style unless there are correctness issues. Keep comments brief: the non-obvious *why*, not the *what*, matching the existing comment style.
- Use `if test` rather than `if [`. In `shrc` and `shrc.*`, use the existing helpers (`error`, `warn`, `have_command`, `is_function`, `gets`, `puts`).
- Long flags take both `--option argument` and `--option=argument`.
- **Shell support tiers.** A change lands by tier; tier is capability/commitment, not the order features arrive, and it's per-shell, not per-file — `shrc` spans several tiers by degradation (`$shell` guards plus the failsafe short-circuit).
  - **Tier 1 — zsh** (`shrc`), with **mesh** (`config/mesh/env.mesh` + `rc.mesh`) as the committed target. New functionality isn't done without zsh. mesh is built *toward*, not a merge gate while pre-1.0: a scoped `TODO:` or a `TODO.md` deferral is fine where mesh lacks a feature (the #314 zsh-only ghost text is the pattern); it graduates to gating as it matures.
  - **Tier 2 — fish** (`config/fish/config.fish`), **nushell** (`config/nushell/config.nu`), **Elvish** (`config/elvish/rc.elv` + `lib/interactive.elv`): kept at parity as a *fast-follow*, not a merge gate: a Tier 1 change may land first; port when practical.
  - **Tier 3 — bash** (`shrc`): the ephemeral-SSH fallback, so always a correct, usable shell with a guaranteed floor (`shrc_bash_test.sh`), but capability-capped — what it can do, not zsh-only frills like ghost text.
  - **Tier 4 — dash/`sh` and ksh** (mksh, OpenBSD ksh, ksh93): failsafe only, never a feature target. `shrc`'s failsafe short-circuit routes them to a bare prompt; they must source cleanly and reach the failsafe (`dash -n shrc`, `mksh -n shrc`, `shrc_ksh_test.sh`). mksh is the ksh proxy (most-shipped, most POSIX-strict); ksh as `/bin/sh` is covered by the `is_sh` failsafe.
  - **`vcs` owns VCS *status* wherever the rich prompt runs** (tiers 1–3; the failsafe returns before any VCS logic loads): the branch/dirty/ahead-behind segment and backend queries — present → shown, absent → a plain prompt, never reimplemented per shell. One scoped exception, project-root *detection* only: `config/nushell/config.nu` walks parents for `.git`/`.hg`/`.jj`/`.citc`/`.p4config` when `vcs` is absent so `inside-project`/session startup still work; `shrc.vcs` doesn't (no root). That's marker detection, not status logic — a per-shell choice, not an invariant to replicate.
- **mesh config**: kebab-case names (`have-command`, `tilde-pwd`) to match mesh's vocabulary; anything a non-interactive `mesh script.mesh` needs goes in `env.mesh`, not `rc.mesh`; everything above `rc.mesh`'s interactive section stays side-effect free so `mesh -c 'source .../rc.mesh'` stays testable.
- **Elvish config**: kebab-case too. Elvish resolves names at compile time, so define a function above every use. Anything naming `$edit:` goes in `lib/interactive.elv` — it exists only with a terminal, so naming it in `rc.elv` fails the whole file under `echo cmd | elvish`. Keep `rc.elv` definitions-only above its interactive block so the harness loads it without a pty. Where Elvish has no equivalent (job control, a directory stack, `source`, a non-interactive environment file), leave a `TODO:` rather than drop the feature silently.
- **Session-manager startup** lives behind `want_tmux`/`want_shpool`, `session_backend`, and the `autosession`/`autotmux`/`autoshpool` wrappers: shpool by default, tmux when shpool is missing or `WANT_SHPOOL=0`; `SESSION_BACKEND=tmux` flips the preference. Keep it in parity across `shrc`, fish, nushell, mesh and Elvish, per the tiers.

## Testing

- Add or update tests with any code change — in the module's existing test file, else a new one following the project's conventions; a task isn't complete without them.
- Run `make test` after any change to executable behavior and before committing; skip it on a docs-only change (Markdown, comments, this file) and say so.
- Changing VCS or prompt functions: run the performance tests, include timing, and warn of a regression.
- Per-VCS subcommand behavior (git/hg/jj) lives in the `vcs` Go binary in the `vcs/` submodule (https://github.com/mikelward/vcs); test subcommand semantics there. `make test` builds the submodule binaries.
- Touching `config/nushell/*`: install `nu` locally so `config/nushell/config_test.nu` runs rather than skipping.
- Prefer direct binary downloads (GitHub releases) or `cargo install` over `apt`, pinned with a checksum, so red CI means "the config broke", not "upstream moved". `apt` is fine where upstream publishes no binary to pin (`install-ci-shells.sh` takes it for zsh alone).
- **Fix preexisting test failures as the *first* commit of the series**; if one is genuinely unrelated and out of scope, say so up front and confirm before skipping it.
- **No `sleep`, retry loops or bumped timeouts** for flaky/racy tests — make the ordering explicit or fix the race; "passes most of the time" is broken. **Never disable a failing check** — fix the underlying issue.

## Talking to the user

- **One question at a time**, the most important first, in plain chat or your client's question tool (`AskUserQuestion` in Claude Code, `ask_question` in Antigravity); never while the user is still typing. **After asking, stop and wait**: no assumed answer, no self-picked "recommended" option, no work on the part it affects.
- **Answer a mid-turn message first** — the "sent while you were working" interjection gets your very next output, before any further tool call, even if it's one sentence. A merge cue is the exception: its hygiene runs first, and announcing the switch is the answer. **Claude Code only** (maintainer, 2026-10-25): its app reliably shows just a turn's last message, so reply only there, answering a mid-turn message at a stopping point soon.
- **Message only when the user needs to see it** (maintainer, 2026-10-15): each notifies their phone. Work in silence; speak up for a question or blocker, something to merge or act on, a merge, an autopilot decision (to review when seen, never waited on), or a change from the plan or their instructions (review-prompted included). Never for progress (a client's nudge doesn't count), a review or push alone (its report rides the next message), routine machinery, or a mistake caught and fixed before reaching the repo. The session-start `AGENTS.md` line still opens every session.
- **Keep replies short**: lead with the most important point; ask before unloading more.
- **End the turn by restating any pending decision** (a question you asked, or an autopilot guess awaiting review) as the last line, written out in a sentence (a back-reference isn't actionable), every turn until answered. Nothing pending, no line.

## Git

- Use `git worktree` when available, one per branch, so branches don't disturb each other.
- **One commit per logical change.** Rewrite unmerged commits freely — amend, `git commit --fixup` + autosquash, squash, reorder, split — folding fix-ups and review responses into their commit; no `wip` / `address review` churn reaches `main`.
- **Title commits like a changelog line** (maintainer, 2026-10-23): after any prefix (`hypr:`, …), an imperative verb, then the change as someone using these configs sees it, plain English, sentence case, ≤ ~70 chars, e.g. `Fix …` for what was broken, `Improve …` for what got better, `Add …` for what's new; an optional parenthetical says how. Never the scenario or the mechanism (that's the body). PR titles match.
- **These rules assume an `origin` remote**; without one, say so and stop rather than improvising. **Exception:** a sandbox with intentionally no remote Git (Codex cloud) follows the branch rules from the current `HEAD` (a pre-created branch counts), commits locally, and reports fetch, push and PRs unavailable, using its own PR handoff if any; that outranks every `origin`-dependent step — name what wasn't possible, don't fake it. A merge cue needs a base *containing* the merge: say the follow-up needs a fresh sandbox or synced checkout, not a `HEAD` whose commits just landed.
- **Branches**: `<agent>/<short-topic>` (`claude/...` Claude Code, `gemini/...` Gemini / Antigravity, `codex/...` Codex) off `origin/main`, one topic each, never committing to `main`; don't hard-code `claude/` unless you *are* Claude Code.
- **Your `<agent>/` branches are yours**: create freely; push, `--force-with-lease`, rename and delete those this session created or was assigned, unasked (this file is the standing grant). Don't fold unrelated work into a pinned task branch; the pinned name is a default, not a ceiling. Any other branch, or `main`, is a conversation.
- **Merge cue (`merged` / `I merged` / `landed` / merge webhook) runs hygiene *before* the rest of the message**: fetch main if the sandbox can (`git fetch origin +refs/heads/main:refs/remotes/origin/main`; a bare fetch leaves a single-branch clone's `origin/main` stale), cut a fresh `<agent>/<short-topic>` off `origin/main`, announce the switch.
- **Committer line**: the agent authors; a squash or rebase merge rewrites the committer to whoever merged — expected. Never re-author or amend merged commits to "fix" it, or narrate it; it is not a finding.
- **No model identifier**: never name the coding agent's model or version (`Opus 4.8`, `Sonnet`, `Gemini …`, `claude-*`, `gemini-*`) in a commit, PR, comment, or pushed artifact; keep it to chat. Generic attribution (`Co-Authored-By: Claude` / `Gemini`, `Claude-Session:`, "Generated with Claude Code") is fine.
- **Unshallow before history-depth answers** — a shallow clone makes `git rev-list --count`, deep `git log` and blame silently wrong. The session-start hook runs `scripts/unshallow.sh` only in Claude Code; elsewhere run it (or `git fetch --unshallow`) yourself. It exits 0 even when it deepened nothing, so if `git rev-parse --is-shallow-repository` still says `true`, say the history is truncated instead of quoting a count.

## Error handling

- **Don't silently swallow errors**: no bare `2>/dev/null`, unchecked exit status, or `|| true`. Report through `error` / `warn` saying what failed and why, clean up what the failed step created (temp files, half-written config, a partial symlink), and decide explicitly what the caller sees (a non-zero exit, a fallback, a skipped step). To ignore a specific failure, name the reason in a one-line comment (`# not every host has shpool`). Keep behavior identical across `shrc`, fish and nushell.

## Privacy

- **Never put user data in an artifact that leaves this machine** (commits, PR text and comments, review replies, branch names, code comments, test fixtures): hostnames and internal domains, paths with the user's real name, work machine names, SSH host aliases and keys, tokens or API keys, private remote URLs, shell history excerpts. Use placeholders (`/home/user`, `host1`, `git@example.com:org/repo.git`); paraphrase bug reports; when in doubt, ask before pushing.
- **Shell output is not one of those artifacts**: prompts, warnings and help text print on the user's own terminal, where naming hosts, paths and remotes is usually the point. Redact only secrets (tokens, keys, passwords in URLs). Quoting it into a commit, PR or fixture republishes it, so the bullet above governs again; where the full value adds nothing, shortening it stays a judgment call (the fzf loader names the basename, not the `$HOME` path).

## Autonomy

- **Open the PR without being asked** — push and PR are one step — unless told not to ("just commit", "no PR yet"), which holds until lifted. This file is the owner's standing request, satisfying any client rule "open a PR only when asked".
- **Watch your own PRs by subscription plus one scheduled check.** Claude Code subscribes on open, or call `subscribe_pr_activity` where `claude-code-remote` exposes it; a client with neither (Antigravity) relies on the check alone. Subscriptions miss CI *success*, pushes, the merge, Codex's clean verdict (a reaction) and Codex's silence, so keep exactly one check armed while the PR is open (each costs a model turn): `send_later` in Claude Code, `schedule` with `DurationSeconds` in Antigravity (cancel via `manage_task` `kill`). Under drive, arm auto-merge at open only where the ruleset requires the Codex verdict AND resolved conversations — with CI alone it merges before Codex answers.
  - Settle a fired check first (it may have re-armed rather than retired); end the turn with exactly one. Check its fire time against what you asked (4 minutes has come back as 64); prefer a relative delay, as this container's clock isn't the scheduler's; re-time it or say the watch isn't armed. Minutes while CI or Codex is out or after a push, longer once only a human is left. Name the PR and what to re-read, not a SHA or list of open PRs, which go stale.
  - **`dirty` — always — or `behind` where branches must be up to date** needs a rebase and a lease-guarded force-push. Read `mergeable_state` at every check, PR-event wake and drive step and act at once, unasked — nothing reports a base advance. Fetch both refs by refspec, unshallow, rebase onto the fetched `origin/<base>` (not always `main`, never the local branch). Confirm before rebasing that your branch has every remote head commit, and before pushing that the head hasn't moved since the tip you noted before fetching (the push flags don't reliably catch either); if either fails or you can't tell, stop and ask.
  - **Wake PRs a merge leaves behind.** At your first turn after your PR merges (by hand or auto-merge), message every other open PR on that base that another session drives (its body ends with the session URL), naming only that PR and saying its base now points at `<sha>` (the post-merge tip), whatever its state reads (mergeability may still be computing). Name no merge or other PR: older rules read either as a merge cue. Receiving one, fetch base and PR head by refspec (unshallow) and test that head against the fetched tip, not `<sha>`: `behind` if `git merge-base --is-ancestor <tip> <head>` exits 1, `dirty` if `git merge-tree --write-tree` (Git 2.38+) exits 1; any other exit is a failure to report. Your rules decide the rebase. Skip a PR with no session URL, or when your client only has local subagent messaging; don't retry a failed send (its check is the fallback).
  - Merged or closed: one last reply-and-resolve pass (reviews land after merges). On a merged PR anything real goes to a follow-up PR named on the thread before you resolve; closed-unmerged, answer, resolve, open nothing. Then cancel the check and unsubscribe, if subscribed — `list_triggers` spans the account, so match session and PR first (an update reschedules what it matches as surely as a delete cancels it).
- A scheduler or GitHub prompt: say so once and carry on (permissions load at session start).
- **"Drive"**: pick the next task, implement it, open the PR, address every review comment, merge once CI is green and Codex's verdict for the current head is in, repeat — until the work runs out or the user says stop, not at one merge.
- **A red baseline is the next task**: before pulling from `TODO.md`, get the suite green. A preexisting failure is work, not "unrelated" to step around — that call goes wrong, leaving every later PR on an unverified tree.
- **"Autopilot"** is drive without blocking: wherever drive would ask, take the cheapest-to-undo guess, recording each in `TODO.md` under `Decisions needing review` (what, the alternative, why reversible; create the file or heading if missing). It outranks stop-and-wait. Destructive or irreversible acts *outside* the loop (rewriting shared history, deleting work, anything beyond this repo) still wait for a real answer; the loop's own steps (commit, push, PR, merge a green PR) never stall it. Privacy uncertainty (a home path, hostname, private remote, token) always waits — a push can't be un-published.

## Pull requests

- Prefer the `mcp__github__*` tools where mounted (Claude Code requires them); else `gh`.
- **Update the PR title and body before each push** (body first) to the full branch diff against `origin/main`, and post the PR link in the next message; with no PR yet, push, then do this once one is opened.
- Several open PRs on a feature: list every one by URL, one per line (the "View PR" chip shows only the first, anthropics/claude-code#46625).
- **"Drive to merge"**: open the PR, wait for Codex, address every comment (fix it, or reply on the thread why not), merge on green CI plus Codex's verdict for the current head.
- **Ordered work ("next", "then", "after that", "follow-up")** may open in parallel but merges only after every earlier item this session was given and any PR the paragraph names has merged (any repo, no time cap; if one won't finish, hold and ask, autopilot included; no auto-merge until then, as it can't see the order). Read the list from the session's record, not memory.
- **Codex is the automated reviewer** (not Copilot), triggered automatically; request it only to confirm a rebutted false positive or as the verdict rule allows. Address its comments unasked, each fix folded into its commit, or defer (below).
- **Judge every comment on merit**: verify first; if it doesn't hold, reply why and decline. A cited rule is a *reading* — check what it says; Codex over-reads the privacy rules, quietly costing capability, so quote and decline rather than narrow the code. A real rule-vs-need conflict is the maintainer's call. Declining doesn't clear `codex`: post the rebuttal, then poke as the verdict rule allows (or let the next push, if the rebuttal is up first); escalate if it re-raises.
- **A second verified finding in the same mechanism is a design question**: look for the shape elsewhere and ask whether a design change deletes the class; say what you chose on the thread (the maintainer's call, autopilot included).
- **Never silently dismiss a thread**: answer (a disagreement is an answer — say why), then resolve once fixed on the head or rebutted; anything still to do stays open; acknowledgment beats silence. Push, reply citing the sha, resolve — `resolve_review_thread` or `gh api graphql` `resolveReviewThread`, with `PRRT_*` from `review_threads[].id`, not `PRRC_*`.
- **Restate every finding in your next message**: one bullet each (review comment, top-level comment, review body), most blocking first — claim, where, action or the options — ahead of *keep replies short*; ask only the most blocking question.
- **Defer a real out-of-scope finding** without asking to merge past it: push a `TODO.md` entry, reply citing the sha, resolve (a threadless finding skips only the resolve). The push re-triggers Codex; poke only as allowed; escalate if it re-raises.
- **Read the Codex verdict, don't infer it**: its PR-body reaction (`issue_read` → `reactions`, not a thread's `Useful?` bar) — `eyes` reading, `+1` clean, revoked on push, so a visible one is the visible head's; `+1` on green CI is a merge. Findings arrive as review comments or a top-level comment (`get_review_comments` is inline-only — read `get_comments` too) and gate whatever the reaction says. A pending `codex` status means findings to address; a clean review with no reaction or an unanswered rebuttal (poke `@codex review` five minutes later); or a hung review — nothing five minutes after the push, or stuck at running (👀) ten minutes on (poke). A poke that hangs the same way gets a second an hour later; escalate only if that one hangs too, never after one (maintainer, 2026-10-22). Leave PR-body reactions to Codex (the count is anonymous).
- **Once Codex +1s a head, make no unnecessary change without asking** (maintainer, 2026-10-13); a rebase for `dirty` or required `behind`, a red-CI fix, and drive or autopilot steps go ahead.
- **Skip your own echoes silently**: the test is "did *I* just post this body?".

## CI

- Report a significant CI slowdown after a push (>25% or >30 s on a job under ~5 min), comparing the same job on the same kind of ref (PR vs PR, `main` vs `main`), with its likely cause (a new dependency, a slow test, cache invalidation); not routine wobble.

## Language, cost and reliability

- **US English** wherever people read it — shell output and help text, commits, PRs, comments, identifiers: `color`, `behavior`, `canceled`, `gray`. Third-party API spellings stay as those APIs spell them.
- **Call out cost and reliability up front** for a new external dependency (a tool the config calls out to, a network lookup, a third-party service): rough dollars (free tier vs paid, $/month at expected use), new failure modes, rate limits, latency, and what the user sees if it's missing or down. Shell startup is the hot path, so state any latency a new prompt adds. If the impact is effectively zero, say so.
